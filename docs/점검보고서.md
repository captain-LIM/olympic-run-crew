### B3. 로그인 후 이동 경로(`next`)로 외부 사이트에 보낼 수 있음 (오픈 리다이렉트) — ▶ 실행 확인 (브라우저)

- **수정:** PR #5 (`8cd1592`)
  - [safeNext.ts](../src/lib/safeNext.ts)로 분리했습니다. `next`를 URL로 해석한 다음 **출처(origin)가 현재 사이트와 같을 때만** 허용하고, 해석이 끝난 경로(`pathname + search + hash`)만 돌려줍니다.
  - [AuthForm.tsx:36](../src/components/AuthForm.tsx#L36)은 `safeNext(next, window.location.origin)`을 호출합니다.
  - 문자열이 아닌 값(`?next=`를 여러 번 준 경우의 배열)도 `/`로 처리합니다.
- **원래 문제:** 기존 `safeNext`는 `//`로 시작하는 값만 막았습니다. 브라우저가 `http://example.com/`으로 해석하는 `/\example.com`이 그대로 통과했습니다.
- **브라우저 확인:** 실제 로그인 폼에 입력해 로그인했을 때 도착한 주소입니다.

  | `next` 값 | 수정 전 (`a41ee3a`) | 수정 후 |
  |---|---|---|
  | `/%5Cexample.com` | ❌ `http://example.com/`로 이동 | ✅ `/` |
  | `/%5C/example.com` | ❌ `http://example.com/`로 이동 | ✅ `/` |
  | `//example.com` | ✅ `/` | ✅ `/` |
  | `/account` (정상 경로) | ✅ `/account` | ✅ `/account` |

  - 이 결과로, 최초 점검 때 코드 추적으로만 판단했던 취약점이 **실제로 존재했음**도 확인됐습니다.
  - 외부 이동 여부는 페이지 이동(navigation) 요청만 기준으로 판단했습니다. 외부 사이트로는 실제로 접속하지 않고, 가로채서 기록만 했습니다.
- **단위 테스트:** [safeNext.test.ts](../src/lib/safeNext.test.ts)에 4개를 추가했습니다. 같은 테스트를 기존 로직에 돌리면 "외부 사이트로 해석되는 경로" 테스트가 실패합니다.

### B7. 한 사용자가 같은 공연에 번개를 무제한으로 열 수 있음 — ▶ 실행 확인

- **수정:** PR #10 (`db2e1bc`, `3fc4ab7`)
  - **규칙:** 같은 공연·같은 공연 날짜(KST)에 이미 참여 중인 번개가 있으면 새로 열 수 없습니다. 방장과 참여자 모두 해당하고, 크루에서 나가면 다시 열 수 있습니다. 참여(join)는 제한하지 않습니다.
  - [store.ts:108](../src/lib/store.ts#L108) `createCrew`가 사용자 행을 `FOR UPDATE`로 잠근 뒤 중복을 검사합니다. 이 트랜잭션은 **READ COMMITTED**로 실행합니다([store.ts:135](../src/lib/store.ts#L135), [db.ts:36-40](../src/lib/db.ts#L36-L40)).
  - 409 응답에 이미 참여 중인 번개 id를 넣고([crews/route.ts:58](../src/app/api/crews/route.ts#L58)), 화면에 "참여 중인 번개로 가기" 링크를 보여 줍니다([CrewFinder.tsx:59](../src/components/CrewFinder.tsx#L59)).
- **실행 확인:**
  - **API 시나리오 14개 모두 통과:** 재생성 409와 함께 `crewId`가 기존 번개와 같은지, 다른 날짜·다른 공연·KST 날짜 경계, 참여자 409, 나간 뒤 재생성, 같은 사용자 동시 5건 중 1건 생성, 서로 다른 사용자 8명 동시 생성 모두 성공을 확인했습니다.
  - **화면:** 오류 문구와 링크가 뜨고, 링크를 누르면 기존 번개로 이동합니다(Playwright).
- **격리 수준을 READ COMMITTED로 한 이유 (실측):**

  | 방식 | 같은 사용자 동시 5건 | 서로 다른 사용자 8명 동시 |
  |---|---|---|

### B4·B5·B6 공통: 요청 횟수 제한을 DB에 기록 — ▶ 실행 확인

- **수정:** PR #14 (`9de9a04`, `035560d`)
  - `rate_limits` 테이블([schema.sql:109](../db/schema.sql#L109))과 [rateLimit.ts](../src/lib/rateLimit.ts)를 추가했습니다. 한도는 [`LIMITS`](../src/lib/rateLimit.ts#L22) 한곳에 있습니다.
  - 시간을 고정 구간으로 잘라 `INSERT … ON DUPLICATE KEY UPDATE hits = LAST_INSERT_ID(hits + 1)` **한 문장**으로 셉니다([rateLimit.ts:76-80](../src/lib/rateLimit.ts#L76-L80)). 동시 40건에서 1~40을 정확히 한 번씩 돌려받는 것을 확인했습니다.
  - 서버 메모리가 아니라 DB라서, **재시작하거나 Vercel처럼 서버 인스턴스가 여러 개여도** 같은 기록을 봅니다.
  - 이메일·IP는 **SHA-256 해시로만** 저장합니다. 실제 기록 195행에서 원문은 0건이었습니다.
  - 한도를 넘으면 **429 + `Retry-After`**를 돌려줍니다([api.ts:7](../src/lib/api.ts#L7)).
  - 메모리 방식이던 `auth.ts`의 `attempts`와 채팅 API의 `lastSent`는 지웠습니다.
- **IP 판별:** [`clientIp()`](../src/lib/rateLimit.ts#L55)는 `X-Forwarded-For`의 첫 값을 씁니다.
  - [Vercel 문서](https://vercel.com/docs/headers/request-headers)에 따르면 Vercel은 이 헤더를 덮어쓰고 바깥에서 보낸 IP는 넘기지 않습니다.
  - 반면 로컬 `next start`는 사용자가 보낸 값을 그대로 넘깁니다. Next 소스(`base-server.js`의 `??=`)와 실제 요청으로 확인했습니다. 그래서 이 방식은 Vercel처럼 헤더를 덮어쓰는 앞단을 전제로 합니다.
- **확인 방법:** 같은 시나리오를 수정 전(`c36cc16`)과 수정 후에 돌렸습니다. 서로 다른 IP는 `X-Forwarded-For`로 흉내 냈습니다.

#### B4. 로그인 시도 제한이 약함

- **수정:** [login/route.ts:17](../src/app/api/auth/login/route.ts#L17)에서 **비밀번호를 확인하기 전에** 세 가지 기준으로 셉니다. IP 20회/10분, 같은 IP의 같은 이메일 5회/10분, 이메일 전체 50회/시간입니다. 로그인에 성공하면 센 횟수를 되돌립니다([37](../src/app/api/auth/login/route.ts#L37)).

  | 시나리오 | 수정 전 | 수정 후 |
  |---|---|---|
  | IP A에서 피해자 이메일로 5번 실패 → **IP B의 피해자 본인 로그인** | ❌ 429 (남의 계정이 잠김) | ✅ 200 |
  | 한 IP에서 서로 다른 이메일 20번 실패 → 21번째 | ❌ 401 (계속 시도 가능) | ✅ 429 |
  | 10개 IP × 5번 = 50번 실패 → 새 IP에서 맞는 비밀번호 | 429 (5번 만에 잠김) | ✅ 429 (50번에서 잠김, 의도한 동작) |
  | 같은 IP에서 로그인 25번 성공 | 200×25 | ✅ 200×25 |
  | 같은 IP 동시 40건 실패 | ❌ 401×40 | ✅ 401×20, 429×20 |
  | 5번 실패 → **서버 재시작** → 6번째 | ❌ 401 (기록 사라짐) | ✅ 429 |

- **남은 한계:**
  - IP를 계속 바꾸는 대규모 분산 공격은 IP 제한으로 막을 수 없습니다. 이메일 전체 50회가 마지막 방어선이고, 이 기준에 걸리면 그 계정은 1시간 잠깁니다. 의도한 절충입니다.
  - **Vercel에서 `X-Forwarded-For`를 실제로 덮어쓰는지는 배포 전이라 확인하지 못했습니다.** 아래 "후속 과제"를 참고하세요.

#### B5. 가입 요청 폭주로 서버 자원이 고갈될 수 있음

- **수정:** [signup/route.ts:23](../src/app/api/auth/signup/route.ts#L23)에서 IP당 5회/시간으로 셉니다. 입력 형식 검사 뒤, scrypt 계산([30](../src/app/api/auth/signup/route.ts#L30)) 전입니다. 로그인도 B4처럼 비밀번호 확인 전에 세므로, 막힌 요청은 scrypt를 하지 않습니다.

  | 시나리오 | 수정 전 | 수정 후 |
  |---|---|---|
  | 형식 오류 3번 + 정상 가입 5번 → 6번째 | ❌ 201 | ✅ 429 (형식 오류는 안 셈) |

## 기타 참고

- **개발 서버 로그 오류:** `npm run dev`에서 페이지를 처음 컴파일할 때 `Failed to generate static paths … Unexpected end of JSON input`이 찍힐 수 있습니다. 응답은 정상(200)이었고 `next start`에서는 나타나지 않아, Next 개발 서버 내부 문제로 판단했습니다.
- **Windows에서 curl로 테스트할 때:** 명령줄 인자로 한글을 넘기면 CP949로 전송돼 깨진 문자로 저장됩니다. 앱 버그는 아닙니다. `--data-binary @파일`로 UTF-8 본문을 보내면 정상 저장됩니다.
- **최초 점검 이후 새로 생긴 문제:** `1fa7e0a`에서 들어온 린트 오류로 `next build`가 실패했습니다. PR #3(`3417ca5`)에서 해결했습니다.
- **확인용 스크립트:** 실행 확인에 쓴 Playwright·API 스크립트는 저장소에 넣지 않았습니다. E2E 테스트 환경을 들여올지는 팀에서 정할 일입니다.
