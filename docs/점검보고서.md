### B3. 로그인 후 이동 경로(`next`)로 외부 사이트에 보낼 수 있음 (오픈 리다이렉트) — ▶ 실행 확인 (브라우저)

- **수정:** PR #5 (`8cd1592`)
  - [safeNext.ts](../src/lib/safeNext.ts)로 분리했습니다. `next`를 URL로 해석한 다음 **출처(origin)가 현재 사이트와 같을 때만** 허용하고, 해석이 끝난 경로(`pathname + search + hash`)만 돌려줍니다.
  - [AuthForm.tsx:36](../src/components/AuthForm.tsx#L36)은 `safeNext(next, window.location.origin)`을 호출합니다.
  - 문자열이 아닌 값(`?next=`를 여러 번 준 경우의 배열)도 `/`로 처리합니다.
- **원래 문제:** 기존 `safeNext`는 `//`로 시작하는 값만 막았습니다. 브라우저가 `http://example.com/`으로 해석하는 `/\example.com`이 그대로 통과했습니다.
- **브라우저 확인:** 실제 로그인 폼에 입력해 로그인했을 때 도착한 주소입니다.

  | `next` 값 | 수정 전 (`a41ee3a`) | 수정 후 (`f11ad8a`) |
  |---|---|---|
  | `/%5Cexample.com` | ❌ `http://example.com/`로 이동 | ✅ `/` |
  | `/%5C/example.com` | ❌ `http://example.com/`로 이동 | ✅ `/` |
  | `//example.com` | ✅ `/` | ✅ `/` |
  | `/account` (정상 경로) | ✅ `/account` | ✅ `/account` |

  - 이 결과로, 최초 점검 때 코드 추적으로만 판단했던 취약점이 **실제로 존재했음**도 확인됐습니다.
  - 외부 이동 여부는 페이지 이동(navigation) 요청만 기준으로 판단했습니다. 외부 사이트로는 실제로 접속하지 않고, 가로채서 기록만 했습니다.
- **단위 테스트:** [safeNext.test.ts](../src/lib/safeNext.test.ts)에 4개를 추가했습니다. 같은 테스트를 기존 로직에 돌리면 "외부 사이트로 해석되는 경로" 테스트가 실패합니다.

### B1. 실제로 완주하지 않고 완주 보상을 받을 수 있음 — ▶ 실행 확인

- **위치:** [crews/[id]/route.ts:51-57](../src/app/api/crews/[id]/route.ts#L51-L57), [store.ts:157-159](../src/lib/store.ts#L157-L159)
- **바뀐 점 (`9c391ec`):** 서버가 두 가지를 검사합니다.
  - 체크인과 완주는 "출발 30분 전 ~ 공연 시작 3시간 후" 사이에만 가능합니다.
  - 완주하려면 DB에 이미 체크인이 기록돼 있어야 합니다.

| 세부 항목 | 상태 | 실행 결과 |
|---|---|---|
| 체크인 없이 바로 완주 | ✅ 막힘 | `{"finished":true}` → 409 "먼저 체크인을 해주세요" |
| 한 요청에 체크인+완주 | ✅ 막힘 | `{"checkedIn":true,"finished":true}` → 409 |
| 체크인 창이 열리기 전 체크인 | ✅ 막힘 | 출발 60분 전 → 409 "출발 30분 전부터 체크인할 수 있어요" |
| **출발 전에 완주** | ❌ 남음 | 출발 **20분 전**에 수동 체크인(200) → 바로 완주(200) → 보상 `["handball"]` 지급 |
| **완주를 취소해도 보상 유지** | ❌ 남음 | `{"finished":false}` → 200. 보상은 그대로 `["handball"]` |

- **원인:**
  - 수동 체크인은 위치 확인이 없습니다. 이건 의도된 기능입니다.
  - 완주에 "출발 시각 이후", "코스 소요 시간 경과" 같은 조건이 없습니다.
  - `user_rewards`는 추가(`INSERT IGNORE`)만 하고 지우지 않습니다.
- **수정 방향:**
  - 완주는 `startAt + 코스 예상 소요 시간` 이후에만 허용합니다.
  - `finished:false`를 막거나, 이때 보상도 회수합니다.

## 🟠 완화

### A5. 3D 뷰어가 공연장을 바꿀 때 GPU 자원을 해제하지 않음 — 🔎 코드 추적

- **위치:** [VenueViewer.tsx:154-161](../src/components/VenueViewer.tsx#L154-L161) (`useEffect` 정리 함수)
- **원인 (그대로):** 정리 함수는 `renderer.dispose()`와 캔버스 제거만 합니다.
  - three.js r170의 `WebGLRenderer.dispose()`(`node_modules/three/src/renderers/WebGLRenderer.js:636`)는 렌더러 내부의 목록, 캐시, 이벤트만 정리합니다.
  - 모델의 지오메트리, 재질, 텍스처는 각각 `.dispose()`를 불러야 GPU에서 삭제됩니다. WebGL 컨텍스트는 `forceContextLoss()`를 불러야 닫힙니다.
  - 지금은 회수 시점을 브라우저의 가비지 컬렉션에 맡기고 있습니다.
- **완화된 점 (`9c391ec`):** 큰 모델은 [shouldAutoLoad](../src/components/VenueViewer.tsx#L17)가 조건을 판단해 "3D 불러오기"를 눌러야 받습니다.

  | 화면 너비 | 자동으로 불러오는 모델 |
  |---|---|
  | 1024px 이상 | 모두 (느린 회선·데이터 절약 모드 제외) |
  | 768~1023px | 14MB 이하 (KSPO DOME은 버튼) |
  | 768px 미만 | 6MB 이하 (88잔디마당, 수변무대만) |

  그래서 모바일에서는 무거운 모델이 덜 쌓입니다. **데스크톱에서는 달라진 게 없습니다.**
- **재현:**
  1. 너비 1024px 이상인 화면에서 `/venues`를 열고 개발자도구 콘솔을 켭니다.
  2. 공연장을 로딩이 끝날 때마다 20회 정도 번갈아 누릅니다.
  3. `Too many active WebGL contexts` 경고가 뜨는지, 크롬 작업 관리자(Shift+Esc)의 GPU 메모리가 늘어나는지 봅니다.
- **같은 곳의 미해결 문제:** 캔버스 크기와 카메라 비율을 처음 한 번만 계산합니다([VenueViewer.tsx:95-96](../src/components/VenueViewer.tsx#L95-L96)). 창 크기를 바꾸거나 기기를 돌리면 화면이 흐려지거나 찌그러집니다.

- **원인:** 오류 메시지는 같지만, 계정이 없으면 `!user`에서 바로 끝나 scrypt 계산을 건너뜁니다.
- **수정 방향:** 계정이 없어도 미리 만들어 둔 가짜 해시로 `verifyPassword`를 실행해 시간을 맞춥니다.

### B4. 로그인 시도 제한이 약함 — ▶ 실행 확인

- **위치:** [login/route.ts:12](../src/app/api/auth/login/route.ts#L12), [auth.ts:74-86](../src/lib/auth.ts#L74-L86)
- **실행 결과:** 다른 사람의 이메일로 틀린 비밀번호를 5번 보낸 뒤, 그 사람이 **올바른 비밀번호**로 로그인하면 **429**("10분 후 다시 시도")가 납니다. 남의 계정을 10분간 잠글 수 있습니다.
- **그 밖의 문제 (코드 확인):**
  - 이메일 기준으로만 셉니다. 한 IP에서 이메일을 바꿔 가며 흔한 비밀번호를 하나씩 시도하는 공격(password spraying)을 막지 못합니다.
  - 서버 메모리(`Map`)에 저장합니다. 재시작하면 초기화되고, 서버가 여러 대면 공유되지 않습니다.

### B5. 가입·로그인 요청 폭주로 서버 자원이 고갈될 수 있음 — 📖 코드 확인

- **위치:** [password.ts:7](../src/lib/password.ts#L7) `PARAMS`(N=2^15), [signup/route.ts:21](../src/app/api/auth/signup/route.ts#L21)
- **원인:** scrypt 계산 한 번에 약 32MB의 메모리와 상당한 CPU를 씁니다. 그런데 회원가입에는 요청 횟수 제한이 없습니다.
  - 재점검 시 회원가입에 추가된 것은 서버 쪽 비밀번호 확인 검사(14번 줄) 하나뿐입니다.
  - 형식이 맞는 요청이 몰리면 메모리와 CPU가 고갈될 수 있습니다. 서버 부하 시험은 하지 않았습니다.

### B6. 채팅 도배 제한이 서버 메모리 기반 — 📖 코드 확인

## 📝 정정

### D1. `sharp` 의존성 누락 — 최초 보고서의 서술이 틀림

- **최초 서술:** "[cut-mascot.mjs](../scripts/cut-mascot.mjs#L3)가 `sharp`를 쓰는데 `package.json`에 없어서, 새로 클론하면 바로 실패한다."
- **확인 결과:**
  - `sharp`는 `next`의 선택 의존성(`optionalDependencies: ^0.34.3 || ^0.35.5`)입니다. 그래서 `npm install`을 하면 `node_modules/sharp`(0.35.5)에 설치되고, `import sharp`가 정상 동작합니다.
  - 일반적인 환경에서 "바로 실패"하지 않습니다.
- **남는 위험 (경미):** 명시하지 않은 간접 의존성에 기대고 있습니다. 아래 경우에는 실패할 수 있으니 `devDependencies`에 명시하는 것이 안전합니다.
  - `npm install --omit=optional`로 설치한 경우
  - `sharp`를 지원하지 않는 플랫폼
  - 이후 `next`가 `sharp`를 빼는 경우

### C 표의 심각도

- 최초 보고서는 `vitest`를 moderate로 적었습니다.
- 실제 `npm audit`은 `vitest`를 `tinypool`에 의존한다는 이유로 **critical**로 분류합니다. 위 C2 표에 바로잡았습니다.
