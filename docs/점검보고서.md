## A. 기능 버그

### A1. 크루원 목록에서 차단해도 그 사람의 채팅이 화면에 남음 🔍

- **위치:** [CrewRoom.tsx:93](../src/components/CrewRoom.tsx#L93) `block()`, [CrewRoom.tsx:219](../src/components/CrewRoom.tsx#L219), [CrewChat.tsx:54](../src/components/CrewChat.tsx#L54)
- **재현:**
  1. 브라우저 두 개로 A와 B가 같은 크루에 들어가 각자 채팅을 보냅니다.
  2. B 화면의 **크루원 목록**에서 A를 "차단"합니다.
  3. B의 채팅창에 A의 메시지가 남아 있다가, 새로고침해야 사라집니다.
- **원인:**
  - 채팅은 3초마다 `GET …/messages?after=<lastId>`로 **새 메시지만 덧붙이는** 방식입니다. 서버의 차단 필터는 새로 받는 메시지에만 적용되고, 이미 화면에 받아 둔 메시지는 다시 검사하지 않습니다.
  - 채팅 메시지의 "신고"에서 차단하면 CrewChat이 자기 `onBlocked`로 목록을 직접 거르기 때문에 바로 사라집니다.
  - 반면 크루원 목록의 "차단" 버튼과 "신고"는 부모인 CrewRoom에 있습니다. CrewRoom에는 CrewChat의 메시지 목록에 차단 사실을 알릴 통로(prop·콜백)가 없습니다.
- **관련 문제:**
  - [ReportDialog.tsx:47-48](../src/components/ReportDialog.tsx#L47-L48)이 `/api/blocks`의 성공 여부(`res.ok`)를 확인하지 않고 `onBlocked`를 호출합니다. 차단 저장이 실패해도 화면에는 차단된 것처럼 보입니다.
  - 차단 직전에 출발한 폴링 요청의 응답이 `onBlocked` 뒤에 도착하면, 차단한 사람의 새 메시지가 다시 붙을 수 있습니다(드문 타이밍 문제).
- **수정 방향:** CrewRoom이 차단한 사용자 id 목록을 상태로 들고 CrewChat에 prop으로 내려줍니다. CrewChat은 화면을 그릴 때마다 이 목록으로 거릅니다. 이렇게 하면 타이밍 문제도 함께 해결됩니다.

### A2. 이미 같은 크루에 있는 사람을 차단해도 크루에 그대로 남음 🔍

- **위치:** [store.ts](../src/lib/store.ts) `joinCrew`, `blockUser`
- **재현:** A와 B가 같은 크루에 있는 상태에서 B가 A를 차단합니다. 둘 다 크루에 남고, 멤버 목록에서 서로의 닉네임과 도착 상태가 계속 보입니다.
- **원인:** 차단 관계는 **참여하는 순간**에만 검사합니다. README의 "같은 번개에 매칭·참여되지 않는다"는 설명과 어긋납니다.
- **결정 필요:** 차단 시 한쪽을 크루에서 내보낼지, 멤버 목록에서만 서로 가릴지 정해야 합니다.

### A3. 예측식의 조기 도착 비중이 공연장 규모와 무관함 🔍 (의도 확인 필요)

- **위치:** [prediction.ts:87](../src/lib/prediction.ts#L87), [prediction.ts:98](../src/lib/prediction.ts#L98)
- **현상:** 코드는 `earlyShare = 0.45 × scale`을 만든 뒤 98번 줄에서 다시 `scale`로 나눕니다. 그래서 실제 식은 아래와 같고, `earlyShare`는 결과에 영향이 없는 계산입니다.

  ```
  공연부하 = scale × max(본 도착(t), 0.45 × 조기 도착(t))
  ```

- **영향:** 조기 도착의 **절대량**은 바깥의 `scale` 때문에 작은 공연장일수록 작아집니다. 하지만 본 도착 대비 **비율**은 모든 공연장에서 0.45로 같습니다.

  | 공연장 | scale | 조기/본 도착 비율 | 공연 3시간 전 공연부하 |
  |---|---|---|---|
  | KSPO DOME | 1.00 | 0.45 | 0.45 |
  | 핸드볼경기장 | 0.52 | 0.45 | 0.23 |
  | 우리금융아트홀 | 0.22 | 0.45 | 0.10 |

- **결정 필요:** 작성 의도에 따라 고치는 방법이 달라집니다.
  - **(A) 절대량만 줄이는 게 의도였다면:** 결과는 맞습니다. `earlyShare`를 지우고 상수 0.45를 쓰면 됩니다.
  - **(B) 비율까지 줄이는 게 의도였다면:** 조기 도착 항에만 `scale`을 한 번 더 곱해야 합니다. 이 경우 우리금융아트홀의 공연 3시간 전 부하는 약 0.02가 됩니다.
  - KSPO DOME은 scale이 1이라 어느 쪽이든 결과가 같습니다. 중·소형 공연장은 `crowdFrom`과 `walkWindow`가 달라질 수 있습니다.
  - 현재 테스트는 "큰 공연장의 최고 혼잡도가 더 높다"만 검사해서, 어느 식이든 통과합니다.

### A5. 3D 뷰어에서 공연장을 바꿀 때 GPU 자원을 해제하지 않음 🔍

- **위치:** [VenueViewer.tsx:137-144](../src/components/VenueViewer.tsx#L137-L144) (`useEffect` 정리 함수)
- **현상:** 공연장을 바꿀 때마다 새 `WebGLRenderer`(새 WebGL 컨텍스트)를 만들고 모델을 GPU에 올립니다. 그런데 정리 함수는 `renderer.dispose()`와 캔버스 제거만 합니다.
- **근거:** three.js r170의 `WebGLRenderer.dispose()`는 렌더러 내부의 목록, 캐시, 이벤트만 정리합니다. 확인 위치는 `node_modules/three/src/renderers/WebGLRenderer.js:636`입니다.
  - 모델의 지오메트리, 재질, 텍스처는 각각 `.dispose()`를 불러야 GPU에서 삭제됩니다.
  - 컨텍스트를 닫으려면 `forceContextLoss()`가 따로 필요합니다.
  - 지금은 회수 시점을 브라우저의 가비지 컬렉션에 맡기고 있습니다.
- **재현 방법:**
  1. `/venues`에서 개발자도구 콘솔을 엽니다.
  2. KSPO DOME(26MB) ↔ 핸드볼을 로딩이 끝날 때마다 20회 정도 번갈아 누릅니다.
  3. `Too many active WebGL contexts` 경고가 뜨는지, 크롬 작업 관리자(Shift+Esc)의 GPU 메모리가 늘어나는지 봅니다.
- **같은 곳의 문제:** 캔버스 크기와 카메라 비율을 처음 한 번만 계산해서, 창 크기를 바꾸거나 기기를 돌리면 화면이 흐려지거나 찌그러집니다.
- **수정 방향:**
  - 정리 함수에서 모델을 순회하며 지오메트리, 재질, 텍스처를 `dispose()`하고 `renderer.forceContextLoss()`를 호출합니다.
  - `ResizeObserver`로 크기 변화에 대응합니다.

## B. 보안 취약점 (코드)

### B1. 체크인 없이 완주 처리하고 보상을 받을 수 있음 ✅

- **위치:** [crews/[id]/route.ts:56](../src/app/api/crews/[id]/route.ts#L56)
- **재현:** 크루 멤버가 체크인하지 않은 상태에서 `PATCH /api/crews/<id>`에 `{"finished":true}`를 보냅니다. 200이 오고, `/api/auth/me`의 `unlocked`에 공연장이 추가됩니다.
- **추가 문제:**
  - 출발 시각 전에도 완주 처리할 수 있습니다.
  - `{"finished":false}`로 되돌려도 보상은 남습니다.
- 설계서 13장에도 "완주 검증" 한계로 적혀 있지만, 보상을 위조할 수 있으므로 보안 항목으로도 분류했습니다.

### B2. 로그인 응답 시간으로 가입된 이메일인지 알 수 있음 ✅

- **위치:** [login/route.ts](../src/app/api/auth/login/route.ts) `if (!user || !(await verifyPassword(...)))`
- **재현:** 틀린 비밀번호로 로그인을 시도해 응답 시간을 비교합니다.

  | 이메일 | 응답 | 걸린 시간 |
  |---|---|---|
  | 가입된 이메일 | 401 | 약 90ms |
  | 없는 이메일 | 401 | 약 4ms |

- **원인:** 오류 메시지는 같지만, 없는 계정이면 scrypt 계산을 건너뛰어서 응답 시간이 다릅니다.
- **수정 방향:** 계정이 없어도 미리 만들어 둔 가짜 해시로 `verifyPassword`를 실행해 시간을 맞춥니다.

### B3. 로그인 후 이동 경로(`next`) 검사의 허점 🔍 (브라우저 확인 필요)

- **위치:** [AuthForm.tsx:11](../src/components/AuthForm.tsx#L11) `safeNext`
- **재현:** `/login?next=/%5Cexample.com`(`%5C` = `\`)으로 접속해서 로그인합니다.
- **원인:** `//`로 시작하는 경로만 막습니다. 브라우저는 URL의 `\`를 `/`로 해석하므로, `/\example.com`이 외부 사이트로 이동하는 오픈 리다이렉트가 될 수 있습니다.

### B4. 로그인 시도 제한이 약함 🔍

- **위치:** [login/route.ts:12](../src/app/api/auth/login/route.ts#L12), [auth.ts:74](../src/lib/auth.ts#L74)
- **문제:**
  - **이메일 기준으로만 셉니다.** 한 IP에서 이메일을 바꿔 가며 흔한 비밀번호를 하나씩 시도하는 공격(password spraying)을 막지 못합니다.
  - **서버 메모리에 저장합니다.** 재시작하면 기록이 사라지고, 서버가 여러 대면 공유되지 않습니다.
  - **남의 계정을 잠글 수 있습니다.** 다른 사람의 이메일로 틀린 비밀번호를 5번 보내면 그 사람이 10분간 로그인하지 못합니다.

### B5. 가입·로그인 요청 폭주로 서버 자원이 고갈될 수 있음 🔍

- **위치:** [password.ts](../src/lib/password.ts) `PARAMS`(N=2^15), 회원가입 API
- **원인:** scrypt 계산 한 번에 약 32MB의 메모리와 상당한 CPU를 씁니다. 그런데 회원가입에는 요청 횟수 제한이 없습니다. 동시 요청이 몰리면 메모리와 CPU가 고갈될 수 있습니다.

### B6. 채팅 도배 제한도 서버 메모리 기반 🔍

- **위치:** [messages/route.ts:10](../src/app/api/crews/[id]/messages/route.ts#L10)
- **문제:** B4와 같은 구조입니다. 재시작하면 초기화되고, 서버가 여러 대면 공유되지 않습니다.

### B7. 한 사용자가 같은 공연에 번개를 무제한으로 열 수 있음 🔍

- **위치:** [crews/route.ts:56](../src/app/api/crews/route.ts#L56)
- **문제:** 같은 조건으로 `POST /api/crews`를 반복하면 번개가 계속 생성됩니다. 같은 공연의 매칭 목록을 스팸으로 채울 수 있습니다.
